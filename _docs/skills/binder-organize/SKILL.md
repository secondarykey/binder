# Binder ノート整理

バインダー（Binder のデータディレクトリ）のメモを読み、対話で方針を決めて、
ノートの本文・階層・図を実際に書き換える。

## このスキルの前提

作業ディレクトリは **バインダー**（`binder.json` を持つ git リポジトリ）であって、
Binder アプリのソースリポジトリではない。`binder.json` が無ければ即座に中断すること。

バインダーのデータ構造・CSV の列定義・エスケープ規則は `reference/data-model.md`、
Markdown 中の描画関数は `reference/render-functions.md`、
操作別の具体手順は `reference/recipes.md` にある。**書き込みを行う前に
`reference/data-model.md` を必ず読むこと。**

## 実行フロー

### 0. 前提チェック（必須・省略不可）

```
powershell -ExecutionPolicy Bypass -File <skill>/scripts/Preflight.ps1
```

チェック内容と中断条件:

| 項目 | 中断条件 |
|---|---|
| `binder.json` の存在 | 無ければ**中断**（ここはバインダーではない） |
| `.git` の存在 | 無ければ**中断** |
| `.git/index.lock` | 有れば**中断**（Binder が動作中の可能性） |
| `git status` | 汚れていれば**中断**（先にアプリで記録してもらう） |
| `db/*.csv` のヘッダ行 | 出力された列順・列有無をこの回の作業前提として固定する |
| `CONTAINERS=` の行 | 未完成マーカーの書式が決まる（下記「未完成箇所のマーカー」） |

**さらにユーザへ明示的に確認する**: 「Binder アプリでこのバインダーを開いていませんか？
開いていれば閉じてください」。go-git は `.git/index` を lock ファイルを介さず直接書き込むため、
アプリと同時に編集するとインデックスが壊れる。

### 1. 読み込みと現状レポート

- `db/structures.csv` から `parent_id` + `seq` でツリーを構築する
- `notes/*.md` を全て読む。`diagrams/*.md`（Mermaid 生ソース）も読む
- `assets/` 配下のバイナリは**読まない**（サイズが大きく意味も無い）

ユーザに次を提示する:

- ツリー図（名前・type・ノートの行数）
- 各ノートの一行要旨
- 気になる点（index 直下に溜まった未整理ノート、重複した話題、極端に長い/短いノート、
  参照が壊れている `{{...}}`、公開済み/未公開の別）

### 2. 設問（AskUserQuestion を 1 回・最大 4 問）

現状レポートを踏まえ、**そのバインダーの実態に即した選択肢**を作って聞く。汎用の雛形:

- **目的** — 散らばったメモを統合 / 長文を章立てして分割 / ツリーを再編 / 要約・目次ノートを追加
- **対象範囲** — 全体 / 特定のサブツリー / index 直下の未整理分のみ
- **出力方針** — 新規ノートを作って元は残す（既定） / 既存ノートを直接書き換える
- **図** — 本文から Mermaid 図を起こして差し込む / 図は触らない
- **未完成マーカーの書式** — Preflight が `CONTAINERS=available` を出した場合のみ。
  選択肢は 2.5 の表の 3 つをそのまま使う（この設問もここでまとめて聞く）

### 2.5. 未完成箇所のマーカー（スクリーンショット待ち等）

まとめの途中で「ここに画面を貼りたいが自分では用意できない」箇所が必ず出る。
**HTML コメント（`<!-- TODO -->`）は使わないこと。** プレビューに何も出ないため、
読んでいるときに気づけない。

**Preflight の `CONTAINERS=` を見て書式を決める:**

`CONTAINERS=active` — `containers.js` が有効。この書式を使う:

```
::: warning TODO: スクリーンショット
手順3の画面（設定タブを開いた状態）を貼る。
:::
```

`containers.js` が出すのは `<div class="container container-warning">` と
`<p class="container-title">` という**クラスだけで、CSS は一切持っていない**。
アプリのテーマにも公開テンプレートにも `.container` の定義は無い。
**スタイルを当てるまでは枠なしの素のテキストとして出る**ので、
下の「スタイルの追加」を必ずセットで行うこと。

`CONTAINERS=available` — ライブラリにあるが未有効。**勝手に有効化しない。散文で聞かず、
`AskUserQuestion` の選択肢として出す**（ステップ 2 の設問に 1 問分として混ぜる）。
header は `マーカー` など。選択肢は必ず次の 3 つをこの順で並べる:

| 選択肢（label） | description | 選ばれたときの振る舞い |
|---|---|---|
| スキルが有効化（推奨） | `~/.binder/plugins/marked/containers.js` をこのバインダーの `plugins/marked/` へコピーし、テーマCSSと公開用CSSに `.container` のスタイルを追記する。バインダー全体の描画が変わり、git で共有され、公開ページにも効く | ファイルをコピーし、下の「スタイルの追加」を行って `:::` 書式を使う |
| 自分でアプリから有効化 | Binder のプラグイン設定から `containers` をインストールする。プラグイン本体はユーザが入れ、スタイルはスキルが当てる | 下の「ユーザ自身が有効化する場合の手順」→「スタイルの追加」へ |
| 有効化しない | プラグインを増やさず、引用ブロック形式のマーカーで済ませる | `CONTAINERS=none` のフォールバック書式を使う |

「スキルが有効化」でもやることはファイルのコピーだけ（設定フラグは無い）で、
アプリのプラグイン設定から入れるのと同じ結果になる。コピーした `plugins/marked/containers.js` は
この回のコミット（ステップ 6）に含め、何を入れたかをメッセージに書く。

**ユーザ自身が有効化する場合の手順**（これをそのまま伝える）:

1. Binder でこのバインダーを開き、プラグイン設定から `containers` をインストールする
2. 増えた `plugins/marked/containers.js` を未記録一覧から記録する
3. **アプリを閉じてから**こちらに戻ってくる

戻ってきたら **Preflight を再実行して `CONTAINERS=active` を目で確認してから** `:::` 書式を使う。
確認しないと、未記録のままだったりアプリが開きっぱなしだったりする。
ユーザが手間だと判断してやめた場合はフォールバック書式に落とす。

#### スタイルの追加（有効化とセットで必須・省略不可）

`containers` を有効化したら（すでに有効だった場合も、`.container` の定義が無ければ）
**2 箇所に CSS を入れる。** どちらか片方だけでは片側で枠が消える。

| 当て先 | 効く範囲 |
|---|---|
| `~/.binder/themes/{theme}.css` | **アプリのプレビュー**。マーカーを読む場所はここ |
| CSS アセット（`assets/{id}`、`assets.csv` の `mime` が `text/css` の行。`layout.tmpl` が `{{assets "{id}"}}` で参照） | **公開HTML**。バインダー内・git 管理下 |

**色や余白を決め打ちしないこと。その当て先の既存の書き方に合わせる。**

- テーマ CSS — 使用中のテーマ id は `~/.binder/setting.json` の `lookAndFeel.theme`。
  ファイルは**先頭の CSS 変数定義（`--accent-orange` `--bg-elevated` `--border-primary` 等）を
  読んでから、その変数を使って書く**。生の `#ffcc00` のような値を直接書かない。
  ダーク/ライトの両方を使うユーザなら両方のファイルに入れる
- CSS アセット — 既存のルールを読み、そこで使われているセレクタの粒度・命名・
  単位・色の指定方法（変数か生値か）に合わせる。公開ページ側は独立した CSS なので、
  テーマの変数は使えないことが多い。その場合はそのファイル内の既存の色に揃える

**テーマ CSS の書き込み先に注意**: `~/.binder/themes/_default/*.css` は
アプリのバージョンアップ（`UpdateDefaults`）で**上書きされる**。編集してはならない。
`~/.binder/themes/{theme}.css`（`_default` の 1 階層上、ユーザディレクトリ）が
同名の `_default` を上書きする仕組みなので、そこに無ければ
**`_default/{theme}.css` をユーザディレクトリへコピーしてから追記する**。

テーマ CSS はバインダーの外にあり、**全バインダー・アプリ全体に効く**。
git 管理外なのでこのスキルのコミットにも含まれず、`git revert` でも戻らない。
書き換えたことと戻し方（該当ブロックを消す）をステップ 7 で必ず伝える。

CSS アセットの側は実体ファイル（`assets/{id}`）を書き換えるだけで、
`assets.csv` / `structures.csv` の行は既存のものをそのまま使う（新規行を作らない）。
変更はステップ 6 のコミットに含める。

`CONTAINERS=none` — フォールバック。プラグイン無しでどこでも見える書式:

```
> ⚠️ **TODO: スクリーンショット** — 手順3の画面（設定タブを開いた状態）を貼る。
```

**どの書式でも `TODO:` という文字列を必ず含めること。** これが全体の共通キーになり、

- `Validate.ps1` が末尾に `TODO :` 一覧（ファイル:行:ノート名）を出す
- ユーザがアプリの**検索**（左メニューの虫眼鏡）で `TODO:` を引けば全件出る
  （検索はノート・図・テキストアセット・テンプレートの**ソースを行単位**で見る）

### 3. 計画提示 → 承認

実行前に、変更予定を 4 分類で列挙する。

1. **新規ノート** — 名前 / 配置先の親 / 元にした素材
2. **移動・並べ替え** — id / 変更前の親 → 変更後の親 / 新しい seq
3. **本文書き換え** — 対象ノート / 何をどう変えるか
4. **新規図** — 図の名前 / 種類（flowchart, sequenceDiagram 等）/ 差し込み先ノート

触る実ファイルと CSV 行も明示する。**削除は既定で行わない。**
不要と判断したノートは「削除候補」として提案するに留め、ユーザが明示的に指示した場合のみ削除する。

承認を得るまで書き込みを開始しないこと。

### 4. 実行

#### モードの選択

**安全モード** — `notes/{uuid7}.md` を書くだけ。CSV は一切触らない。
Binder は次にバインダーを開いたとき `RunDoctor()` で structure 行の無い `notes/*.md` を
検出し、**名前 = id・index 直下**として自動登録する。事故が起きようがないが、
名前と位置はユーザがアプリ側で直す必要がある。
「とりあえず本文だけ作って、整理はアプリでやる」場合や、CSV のスキーマに不安がある場合に使う。

**フルモード** — CSV まで書いて、名前・階層・seq・alias まで確定させる。既定はこちら。

#### フルモードの書き込み順序（厳守）

途中で中断しても doctor が救済できる向きに書く。

1. **実体ファイル** — `notes/{id}.md` / `diagrams/{id}.md`
2. **実体テーブル行** — `notes.csv` / `diagrams.csv`
3. **`structures.csv` 行**

逆順（CSV を先に書く）にすると、中断時に「structure 行はあるが実体ファイルが無い」状態になり、
doctor が**空ファイルを再作成**するため本文が失われる。

#### 書き込みルール（詳細は `reference/data-model.md`）

- `id` は UUID v7。`scripts/New-Uuid7.ps1 -Count N` で生成する（自分で捏造しない）
- `seq` は同一 `parent_id` 内の max+1。再編したら **その親の子全部を `1..n` で振り直す**
- `alias` は note / diagram では **id と同じ値**を入れる（アプリの新規作成と同じ挙動）
- `publish_date` / `republish_date` は新規行では必ずゼロ値 `0001-01-01T00:00:00Z`
  （勝手に公開扱いにしない）
- `name` / `detail` は `,` `"` 半角空白 改行 を `&#44;` `&#34;` `&#32;` `&#10;` にエスケープする
- `notes.csv` の `layout_template` / `content_template` は**同じ親の兄弟ノートからコピー**する。
  既定値を推測しない
- `index`（id が `index` のノート）は削除しない。その `parent_id` は空文字のまま
- 子を持つノートは削除しない（アプリ側の制約に合わせる）
- **列は必ずヘッダ行から決める。** バージョンによって `private` 列が無い、`layers.csv` が
  存在しない等の差異がある

### 5. 検証（必須）

```
powershell -ExecutionPolicy Bypass -File <skill>/scripts/Validate.ps1
```

ERROR が 1 件でも出たら**コミットしない**。修正するか、`git checkout -- .` で
実行前の状態に戻してからユーザに報告する。

検証項目:

- structures の各行に対応する実体ファイルと実体テーブル行があるか
- 実体ファイルに対応する structures 行があるか（orphan）
- `parent_id` が実在するか / 自己参照でないか / index から到達できるか
- `alias` が type 内で一意か
- 同じ親の中で `seq` が重複していないか
- 各行の列数がヘッダと一致するか（エスケープ漏れによるカンマ混入の検出）
- **`{{drawDiagram "..."}}` `{{assetsImage "..."}}` `{{assets "..."}}` `{{embed "..."}}`
  `{{drawLayer "..."}}` の参照先 ID が実在するか**

### 6. コミット

```
git add -A
git commit -m "..."
```

`db/*.csv` の変更は Binder の「未記録一覧」に出ない（アプリ側で管理外扱い）ため、
未コミットで残すとユーザから見えない。必ずスキル側でコミットする。

メッセージは「何をまとめたか」の要約 + 変更点の箇条書き。
バインダーはユーザの文書リポジトリなので、Binder 開発の Conventional Commits 規約は適用しない。

### 7. 事後案内

ユーザに次を伝える:

- 次に Binder でこのバインダーを開くと `RunDoctor()` が整合性を検査すること。
  修復が報告されたら CSV の書き損じなので知らせてほしいこと
- 追加・変更したノートは**未公開のまま**であること。公開したければアプリの
  「未公開一覧(Publish)」から生成・送信すること
- **元に戻す手順は必ずアプリの操作で案内すること。`git revert` 等の git コマンドを
  復元手段として提示してはならない**（下記「元に戻す案内」）
- **残っている `TODO:` を Validate の出力そのままで一覧提示すること**（ファイル:行:ノート名）。
  アプリの検索で `TODO:` を引けば同じものが出せることも一度は伝える
- テーマ CSS を書き換えた場合は**そのファイルパスと追記したセレクタ**を伝えること。
  バインダーの外にあるため今回のコミットに含まれず、履歴からの復元でも戻らない。
  戻したければそのブロックを消せばよいことも添える

#### 元に戻す案内

Binder のユーザは git を使えるとは限らない。UI も git 用語を隠している。
コミットハッシュを渡して終わりにせず、**アプリのどこを押せばよいかを書く**。

コミット後に `git log -2 --format='%h %ad %s' --date=format:'%Y-%m-%d %H:%M'` で
**自分が作った記録とその1つ前**の短縮ハッシュ・日時・メッセージを取り、次の形で伝える:

> 元に戻したい場合は、左メニューの **履歴** → **全体履歴** を開き、
> 今回作成した記録（`703f8a9` / 2026-08-29 14:32「ノート整理」）の **1つ前** の記録を選んで
> **復元する** を押してください。

**「1つ前」を選ばせるのが要点。** 全体履歴の復元は「選んだ記録の状態に全ファイルを戻す」
（`git revert` のような差分の打ち消しではない）。今回の記録を選ぶと、
整理後の状態がそのまま復元されて何も戻らない。**1つ前の記録の短縮ハッシュと日時も
併せて出す**と迷わない。

補足として伝えてよいこと:

- 復元しても履歴は消えない。**新しい記録として積まれる**ので、やり直しも復元でできる
- 特定のノートだけ戻したいなら、そのノートを開いて **更新履歴** から
  そのファイルだけ **復元する** ことができる
- 復元前に未記録の変更があると消える（アプリが警告を出す）

## やらないこと

- バイナリアセットの新規追加・変換
- `docs/` 配下の公開 HTML の生成（アプリの公開機能の責務）
- `templates/` の編集（レイアウトの責務。壊すと全ページの表示が崩れる）
- Binder アプリ本体のソースコードの変更（それは別のスキルの領分）
