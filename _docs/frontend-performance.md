# フロントエンドの高速化（済んだもの・残り）

2026-11-12 にエディタ画面（`/editor/:mode/:id`）を中心に見直した記録。
済んだものと、手を付けていない候補を残す。候補はどれも**実機で測っていない**ので、
着手する前に「どこが遅いか」を測ってから決める（下の「測り方」）。

## 済んだもの

| 内容 | コミット |
|---|---|
| ノート・図を切り替えるときの点滅をなくす | 9e5e195b |
| アセット（画像）を開くとき・切り替えるときの点滅をなくす | 3d1b78ff |
| 打鍵のたびにツールバーとダイアログを描き直さない | 25633bb9 |

### 点滅（9e5e195b）

プレビュー（`HTMLFrame`）は 2 枚の iframe を裏で描いてから切り替える作りだが、手前の処理が打ち消していた。

- 変換のたびにプレビューへ「Loading...」を挟んでいた → やめた。変換が終わるまで前の表示を出したままにする
  （処理中であることはステータスバーに出る）
- 同じ種類のまま開き直すときも本文を一度空にしていた → ノート→ノート、図→図では空にしない。
  本文が前と同じでも描画し直せるよう、開き終えた回数（`openSeq`）でも `useEffect([text])` を起こす
- 行番号の折り返し行数を「何行目か」で持っていた → 行の内容から引く。測っていない行が複数あるときは描画の前に測る

このとき決めたこと（戻すと点滅やデータの取り違えが戻る）:

- 読んでいる間（`loadingRef`）の入力は受け付けない。前の本文が新しい側の ID で保存されるのを防ぐ
- 追い越された読み込み・変換の結果は捨てる（`idRef.current !== id`）
- プレビューのカーソル行（`cursorLine`）は HTML と同時に渡す。先に渡すと、差し替える前の表示がその行へ動く

**テンプレートの切り替えは触っていない**（本文を一度空にする動きが残る）。プレビューに使うノート・相手の
テンプレートの選択など絡む状態が多いので、直すなら実機で動かしながら。

### アセットの点滅（3d1b78ff）

`AssetViewer.jsx` に 2 つあった。

- 画像（`ImageViewer`）は読み込んだ直後は左上・等倍で、`onLoad` で初めて収まる倍率と中央の位置にしていた
  → 位置が決まるまで `visibility: hidden` にする
- 開くたびに中身を空にして「Loading...」を挟んでいた → **画像から**切り替えるときは、次が届くまで前の画像を出したままにする

決めたこと:

- テキスト・SVG から切り替えるときは今までどおり空にする。編集できるので、残すと前の本文への入力が新しい ID で保存される
- 前の画像を出している間（`switching`）はダウンロードを止める（中身と ID が食い違うため）。
  メタ情報（`assetMeta`）は今までどおりすぐ空にする（ファイルの更新などが前のアセットに向かわないように）
- 追い越された読み込みの結果は捨てる（`idRef.current !== id`）

### 打鍵時の再描画（25633bb9）

エディタ本体（`Component.jsx`）は 1 文字ごとに全体が描き直される。次を `memo` にして巻き込まれないようにした:
`EditorToolbar` / `PreviewToolbar` / `ParseDialogs` / `PreviewContextMenu` / `FontDialog` / `TableDialog`、
行番号ガター（`EditorArea` の `LineNumbers`）。

本体から渡すハンドラは `useStableHandlers`（`components/editor/useStableHandlers.js`）を通す。
**memo にした部品へ、描画のたびに作り直される関数や配列・オブジェクトをそのまま渡すと memo が効かなくなる**。
部品へ props を足すときは、ハンドラは `useStableHandlers` に足し、配列は `useMemo` にする。

### git status のキャッシュ（c4261986）

残りの候補 1 のために Go 側を測ったところ、ノートのメタ情報を取る `Binder.GetNote` の半分は
DB ではなく git の状態確認（`fs.getStatus` → `modified`）だった。呼ばれるたびにワークツリー全体の
`worktree.Status()` を取り直していて、ノート数に比例して遅くなる。未公開一覧（`GetUnpublishedNotes` など）は
全件を順に確かめるので、件数 × 全体の走査になっていた。

素の git status を `FileSystem.worktreeStatus()` でキャッシュした。有効期間（2 秒）と無効化（`invalidateStatus`）は
`Status()` のキャッシュと同じ。**ワークツリーやインデックスを変える処理を `fs` に足すときは `invalidateStatus()` を呼ぶ**
（呼ばないと、最大 2 秒のあいだ更新の印が古いままになる）。

200 ノートのバインダーでの計測（テスト用の一時的なコードで測った。OS のファイルシステム上）:

| | 前 | 後 |
|---|---|---|
| `fs.SetNoteStatus`（1 回） | 3.3ms | 0.4ms |
| `Binder.GetNote`（1 回） | 6.7ms | 4.0ms |
| `GetUnpublishedNotes`（公開済み 200 件） | 923ms | 28ms |

### 文字数（07eeb915）

`countChars` は打鍵のたびに本文全体を数える。5000 行（25 万文字）で 2.6ms → 0.4ms（node で計測）。

## 残り（未着手）

効きそうな順。**1〜3 は 2026-11-12 に測って「いまはやらない」とした**（数字は各項）。

### 1. ノートを開く経路の呼び出しを減らす（測った。いまはやらない）

ノートを開いてプレビューが出るまでに、Go 側を次の順で呼んでいる。

1. `OpenNote` と `GetNote`（並行）
2. `ParseNote`（テンプレート関数の展開）
3. フロントで marked
4. `CreateNoteHTML`（レイアウトへの埋め込み）
5. iframe の読み込み → 図（Mermaid）の描画

`GetNote`・`ParseNote`・`CreateNoteHTML` は、それぞれ Go 側で同じノートのメタ情報を引いている
（`api/html.go` / `api/note.go`）。打鍵後のプレビュー更新（500ms のデバウンス後）でも 2〜4 が毎回走る。

測った結果（git status のキャッシュを入れたあと。200 ノート、1 回あたり）:

| | 時間 |
|---|---|
| `db.GetNote`（csvq） | 1.3〜1.5ms |
| `db.GetStructure`（csvq） | 1.6〜1.9ms |
| `Binder.GetNote`（上の 2 つ + 状態確認） | 4.0ms |
| `Binder.ParseNote`（テンプレート関数の無い本文） | 0.1〜0.2ms |
| `Binder.CreateNoteHTML`（既定のレイアウト） | 6〜7ms |

プレビュー 1 回で Go 側は 4 + 0.2 + 4 + 7 ≒ 15ms。500ms のデバウンスのあとなので体感には出ない。
csvq の問い合わせはノート数に比例する（800 ノートで約 2 倍）ので、数千ノートのバインダーで
ステータスバーの「Success (○ms)」が大きくなったら次を考える。

- メタ情報を Go 側で短い間覚える（`ParseNote` と `CreateNoteHTML` で 1 回ぶん = 3〜4ms 減る）
- `CreateNoteHTML` の 6〜7ms の内訳を見る（テンプレートの読み込みは 0.1ms。残りはレイアウトのテンプレート関数が引く DB）
- 開くときの `OpenNote` + `GetNote` を 1 回の呼び出しにまとめる

### 2. 長いノートでの入力（JS の計算は小さい。残りは実機の Profiler で）

打鍵ごとに残っている処理と、5000 行（25 万文字）での時間（node で計測。React の描画・DOM は含まない）:

- 全体の文字数（`countChars(text)`）: 0.4ms（上で速くした）
- `EditorArea` の行ごとの `split` / キャッシュ引き（3 回ぶん）: 0.6ms、行番号のキー（`wrapsKey`）: 0.4ms
- 保存の状態（`saveState`）の更新によるステータスバーの描き直し（小さい部品。未計測）
- 検索バー（`SearchBar`）を開いている間は、本文を渡しているので一緒に描き直される（中で何をし直しているかは未確認）
- textarea は制御コンポーネントなので本文全体を渡し直す（ブラウザ側の時間。node では測れない）

JS の計算は合わせて 2ms に満たないので、これ以上は削らない。数千行のノートで重いなら、
React DevTools の Profiler で 1 打鍵に何が何 ms 掛かっているかを見る。
textarea を非制御にする（本文を state で持たない）のが一番効くが、`text` を見ている箇所が多く、
`_cmd/binder/frontend/AGENTS.md` にあるとおり**動かして確かめずに分けない**。

### 3. プレビューの差し替え（図の使い回しは実装済みだった）

プレビューは変換のたびに iframe を丸ごと読み込み直している（srcdoc）。

図の SVG は `Mermaid.parse` がすでにキャッシュしている（`engines/Mermaid.jsx` の `_svgCache`。
キーは図のソース全文 + スタイルテンプレート、50 件まで、mermaid の初期化のたびに捨てる）。
`HTMLFrame.postProcess` もここを通るので、図のソースが同じなら描き直さない。追加の作業は無い。

残るのは iframe の読み込み直しそのもの（HTML のパース・CSS の適用・画像の読み込み）。
差分だけ書き換える案はあるが、スクリプトの扱い（sandbox）やリスナの付け直しが絡むので、
長いノートでプレビューの更新が遅いと分かってから。

### 4. バンドルの分割

本体は 1 チャンク（1.19MB、gzip 340KB）。mermaid（5.2MB）と marked は別ファイルで、アイドル時に読み込む。
別ウィンドウ（履歴・全体履歴・プレビュー・ログ・検索）の入口も同じチャンクに入っている。

案: `main.jsx` で入口ごとに `import()` へ分ける。ローカルから読むので、起動が少し速くなる程度の見込み。
起動が遅いと感じるようになってからでよい。

### 5. ツリー

遷移のたびにツリーを取り直してはいない（確認済み）。`BinderTree` は本体から `memo` で遮断してある。
ノードが数百を超えて展開・選択が重くなったら、`Tree.jsx` の各ノードを `memo` にする・見えている範囲だけ描く、を考える。

## 測り方

- **プレビューの変換時間**: プレビュー下のステータスバーに「Success (○ms)」と出る（`ParseNote` 〜 `CreateNoteHTML` の合計）
- **描画**: `task dev` で起動し、WebView の開発者ツール（F12）の Performance、または React DevTools の Profiler
- **Go 側の処理**: ルートパッケージに一時的なテスト（`test.CreateBinder` でバインダーを作り、ノートを数百件足して
  `time.Since` で測る）を書くのが早い。`b.db` / `b.fileSystem` を個別に測るには、同じく一時的な
  `package binder` の `_test.go` に薄いメソッドを足す。測り終えたら消す
- **Go 側の API**: 各 API は `log.PrintTrace` を呼んでいるが、2026-11-12 時点の普段のログには所要時間の行が出ていなかった。
  測るときはログの出し方（レベル）を確かめるか、対象の API に一時的に計測を入れる
